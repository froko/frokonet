# AGENTS GUIDE FOR FROKONET

_Last updated: 2026-02-06_

## 1. Purpose

- Orient agentic contributors working inside
  `/Users/patrickineichen/Work/frokonet`.
- Follow these notes before running commands or editing files; prefer pnpm.
- There are no Cursor rules or GitHub Copilot instructions, so this file is
  authoritative.
- Keep user-owned changes intact; avoid reformatting files you do not touch
  functionally.

## 2. Quick Snapshot

- Stack: Astro 5, Vite, strict TypeScript, Tailwind CSS v4, DaisyUI (Catppuccin
  Macchiato).
- Module format is ESM with `type: module`; linting relies on
  `@froko/eslint-config` plus Astro plugin.
- Prettier comes from `@froko/prettier-config` with Astro + Tailwind plugins for
  class sorting.
- Path aliases (`tsconfig.json`) expose `@components`, `@data`, `@layout`,
  `@library`, `@sections`.
- Static assets prefer `astro:assets` imports or `/public` references.

## 3. Repo Layout Cues

- `src/pages/` holds routed `.astro` files; `_sections` contains homepage slices
  re-exported via `index.ts`.
- `src/components/` stores shared UI (`Head`, `NavBar`); they are
  barrel-exported for alias imports.
- `src/layout/` defines shells (`Page`, `Article`) that import
  `../style/global.css` once.
- `src/data/` exposes small typed modules (navigation, future content) consumed
  through `@data`.
- `src/style/` contains Tailwind entrypoint and the Catppuccin DaisyUI plugin
  shim.
- `public/` holds raw assets such as `me.jpg` and `favicon.svg`.
- Generated folders (`.astro/`, `dist/`) should never be edited manually.

## 4. Tooling & Environment

- Use pnpm (lockfile present); mixing package managers will desync dependencies.
- Node 20+ is recommended for Astro 5 and Tailwind 4 compatibility.
- Vite plugins are limited to Tailwind and `astro-icon`; keep additional plugins
  minimal.
- Run commands from repo root unless a script specifies another cwd.

## 5. Core Commands

- `pnpm install` — install dependencies after cloning or pulling lockfile
  changes.
- `pnpm dev` — start Astro dev server at `http://localhost:4321` with hot
  reload.
- `pnpm build` — produce the static bundle in `dist/`; run before shipping or
  testing preview-only issues.
- `pnpm preview` — serve the production build locally to validate routes and
  assets.
- `pnpm astro sync` — refresh autogenerated `.astro/types.d.ts` when content
  collections change.
- `pnpm astro <subcommand>` — access CLI utilities such as `astro add`,
  `astro check`, `astro docs`.
- `pnpm format` — run Prettier over the repo and then `eslint . --fix` (combined
  formatter + linter).
- `pnpm astro check --watch <path>` — focus diagnostics on a single file during
  iterative work.
- `pnpm astro docs` — open the locally cached Astro documentation in a browser
  tab.

## 6. Quality Gates & Type Safety

- Always run `pnpm format` before committing; it enforces Prettier ordering and
  ESLint fixes.
- For lint-only investigations, use `pnpm eslint <globs>` to avoid rewriting the
  repo.
- `pnpm astro check` performs type checking plus Astro diagnostics; treat it as
  the default "test" gate.
- Do not introduce alternative formatters; ESLint already integrates Prettier
  through `withPrettier`.
- Keep frontmatter scripts concise to prevent lint noise and ensure
  tree-shaking.
- Favor small diffs so ESLint output stays readable in CI logs.
- Comment any lint-disable directives with context and delete them once the
  violation is resolved.

## 7. Testing Reality & Single-Test Guidance

- No automated spec runner exists yet (no `pnpm test` script, no `*.test.ts`
  files).
- Use `pnpm astro check --watch src/pages/about.astro` (replace path) when you
  need a file-scoped safety net.
- UI regressions must be validated manually via `pnpm preview` and browser
  inspection.
- If you add Vitest or Playwright, document the new script and a single-test
  invocation here.
- Until a harness exists, describe manual verification steps in PR descriptions.
- Capture manual test steps in commit or PR descriptions so other agents can
  replay them.
- When adding a runner, expose it via `pnpm <script>` so CI and humans share the
  same entrypoint.

## 8. Imports, Modules, and Types

- Prefer alias imports for intra-repo modules; keep relative paths scoped within
  a folder.
- Order imports: Node/builtins → third-party → alias → relative; rely on ESLint
  to flag drift.
- All files should stay in strict TypeScript; avoid `any` unless you add a TODO
  explaining why.
- Destructure `Astro.props` with safe defaults, as seen in `Head.astro`.
- Barrel files (`src/components/index.ts`) ease import ergonomics; update them
  when new modules ship.
- Keep data modules typed via interfaces or const assertions when shapes are
  stable.

## 9. Components, Pages, and Layouts

- Layouts own shared imports like `global.css`; do not re-import them from child
  components.
- Wrap routed pages with `Page` (or `Article`) so the navbar, `<Head>`, and
  theme attributes stay consistent.
- Use slots for composition; avoid duplicating markup across sections.
- Conditional UI should remain declarative (`{navBarTitle && (...)}`) instead of
  manipulating state.
- When interactive behavior is required, prefer DaisyUI primitives or Astro
  islands instead of raw DOM scripts.
- Keep SVGs inline only when they need styling hooks; otherwise use `astro-icon`
  for icons.
- Define layout props with `export interface Props` so Astro infers types across
  pages.
- Re-export new sections through `src/pages/_sections/index.ts` to keep alias
  imports working.

## 10. Styling & Theming

- Tailwind v4 is configured purely through `src/style/global.css`; do not add
  `tailwind.config.js`.
- DaisyUI runs with Catppuccin Macchiato; stick to theme tokens and semantic
  utility classes.
- Leverage Tailwind responsive prefixes (`md:`, `lg:`) for layout shifts as
  demonstrated in `Hero.astro`.
- Custom CSS belongs in component-scoped `<style define:vars>` blocks and should
  stay minimal.
- When repeating prose styles, use `@apply` (see `Article.astro`) instead of
  manual duplication.
- Import images via `astro:assets Image` for optimization; specify `alt`,
  `width`, and `height` when available.
- Prefer DaisyUI utility classes such as `btn` or `navbar` before inventing
  bespoke combinations.
- Share repeated measurements via CSS variables declared through `define:vars`
  to keep markup tidy.

## 11. Data & Content Handling

- Structured content (navigation, future lists) should live under `src/data`
  with explicit exports.
- Keep arrays sorted intentionally and mark them `as const` when immutability
  helps TypeScript infer literal types.
- Reference assets stored in `public/` using absolute paths (`/me.jpg`) to avoid
  brittle relative URLs.
- Consider moving repeated strings into data modules so translations or future
  CMS integrations stay centralized.
- When fetching remote data in frontmatter, sanitize and validate before
  rendering user-facing HTML.

## 12. Accessibility, Error Handling, and Performance

- Use semantic elements (`<nav>`, `<section>`, `<main>`) and ensure heading
  levels descend sequentially.
- Interactive controls (drawer toggles, links) need `aria` attributes and
  keyboard focus styles.
- Wrap async code in `try/catch`; prefer returning fallback UI instead of
  throwing raw errors.
- For redirects or special responses, use `Astro.redirect` and `Astro.response`
  helpers.
- Always run `pnpm build` before handing work back; it validates image pipelines
  and sitemap generation.
- Keep bundles slim by importing icons through `astro-icon` instead of heavy
  third-party scripts.
- Avoid large JSON imports in frontmatter; fetch lazily or move data into
  smaller modules.
- Audit Lighthouse or axe warnings whenever you touch navigation or focusable
  elements.
- Profile large hero images with Astro's image pipeline so optimized assets stay
  under performance budgets.

## 13. Workflow & Troubleshooting

- Start sessions with `git status` to see user in-flight work; never revert
  their changes.
- If Tailwind utilities stop applying, confirm `global.css` remains imported by
  layouts and rerun `pnpm dev`.
- Clear Vite cache issues by deleting `node_modules/.vite` only if the dev
  server misbehaves.
- Regenerate Astro types via `pnpm astro sync` when content schema changes.
- Document any new scripts or workflows in both `package.json` and this file.
- When adding dependencies, prefer `pnpm add <pkg>` to keep the lockfile stable.

## 14. Documentation & Communication

- Update `README.md` and this guide whenever commands, scripts, or conventions
  change.
- Summarize architectural decisions in PR descriptions so reviewers see the
  intent before the diff.
- Mention affected routes, layouts, and data modules in commit messages for
  easier git archaeology.
- Add short inline comments only when logic is non-obvious and remove them once
  the code becomes clear.
- Prefer incremental PRs so design reviews and manual testing stay practical.

## 15. Security & Secrets

- Never commit `.env`, API keys, or credential dumps; `.gitignore` already
  excludes common secret files.
- Define new environment variables inside `src/env.d.ts` and document their
  purpose in PR notes.
- Avoid logging sensitive values; redact tokens before sharing console output in
  tickets.
- Use provider tooling (e.g., `/connect` in OpenCode) to manage credentials
  rather than hardcoding them.
- When integrating external APIs, validate and sanitize responses before
  rendering user-facing HTML.
- Rotate any shared keys immediately if they ever appear in transcripts, diffs,
  or crash logs.

## 16. Exit Checklist

- `pnpm format`, `pnpm astro check`, and, when relevant, `pnpm build` complete
  without errors.
- Updated docs (including this guide) when commands, styles, or tooling changed.
- Git workspace left clean or with intentional staged changes plus notes for the
  user.
- Summarize manual verification steps in your final message so humans can
  reproduce them.
